Findings from 3 runs:
Main conclusion: concurrency helps at small scale, but the 100-ticket run exposed a local Cadence dispatch bottleneck.

10 × concurrency 1: 9.29 workflows/sec.
10 × concurrency 10: 20.24 workflows/sec, about 2.2× faster overall, although average ticket latency rose from 108 ms to 329 ms.
100 × concurrency 25: throughput collapsed to 1.43 workflows/sec, with 17.2 seconds average and 62.7 seconds maximum wait.
The 100-ticket run is not directly comparable because both count and concurrency changed. Still, the slowdown is real:

Cadence logged 20 Async task dispatch timed out warnings.
One immediate diagnostic Child Workflow took 61 seconds to receive its task.
The Cadence container uses ubercadence/server:master-auto-setup with LOG_LEVEL=debug.
It generated about 66 MB of logs during the 90-second diagnostic window, including 1,174 large stack-trace debug entries.
Cassandra showed no warnings or errors.
So the likely bottleneck is the development Cadence server configuration and workflow-task dispatch, not batch.go submission logic. The 25 batch slots stayed saturated: 1.43 workflows/sec × 17.2 sec ≈ 24.6 average in flight.

Other observations:

All 100 workflows completed, with no execution failures.
Zero SLA statuses are expected because this branch’s Child Workflows return DIAGNOSTIC_ONLY.
-batch-sla 1s is currently irrelevant, so this does not benchmark timers.
The zsh: command not found: # message is harmless. Your shell interpreted the pasted comment as a command.
The runs stayed on the isolated mock task list. No Jev call was made.
Before drawing scaling conclusions, switch Cadence logging to info, preferably use a versioned server image, then run a fixed count such as 100 at concurrency 1, 5, 10, and 25, repeated at least three times.
